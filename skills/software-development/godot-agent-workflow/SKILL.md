# Godot AI Agent 协作工作流规范

本 Skill 定义了主控/策划与 AI 编码助手（如 Codex CLI / Claude Code / 本地 Agent）在 Godot 4.x 项目中的标准交互与实现流程。

---

## 一、 核心工作原则 (Core Tenets)

1. **先发现并读取当前工作树中的仓库指令文件**：检查 `AGENTS.md`、`AGENT.md` 及目标目录上级的同类文件，再按实际存在的文件执行。不要因为当前工作树缺少指令文件，就把 Git 历史中的旧版本写回仓库；历史版本最多只可只读参考，因为删除本身可能是用户的未提交决定。
   - 只能在当前仓库指令允许的目录下操作；美术、第三方目录和 Godot 底层配置默认只读，除非任务明确授权。
   - 公共方法、信号、目录命名和场景搭建方式均以当前工作树中的仓库指令为准，不把旧版本规范或其他项目惯例强加给当前任务。

2. **嵌套子实体树与独立小文件夹规则 (Nested Sub-Entities & Sub-Folders)**：
   - `Entities/` 严格采用**自顶向下的树状嵌套结构**。
   - **已确认需要独立维护、复用或单独实例化的小实体/子功能，必须拥有自己的独立小文件夹**（大驼峰 PascalCase）。该规则约束已确定的实体边界，不代表要把用户提到的整个聚合场景自动拆散。
   - 用户说“拆某场景”但同时引用“和之前某关一样”等既有范例时，先检查范例实际拆的是聚合根、视觉层，还是某个子功能；把目标节点路径和“不拆项”写进任务边界后再修改。不得仅按场景名推断拆分层级，因为用户可能指其中的前景/后景对象，而不是主场景。
   - 若用户随后纠正拆分对象，立即停止错误方向；先用目标目录的 `git status --short` 与定点 `git diff` 判断是否已落盘。没有变更就明确说明无需回滚；已有变更则只逆转本轮引入的结构改动，保留用户原有未提交内容，再按正确子对象实施。
   - 目录结构示例：
     ```text
     Entities/
     └── Player/                  <-- 大实体文件夹
         ├── Player.tscn
         ├── Player.gd
         └── Weapons/             <-- 嵌套子实体分类/容器文件夹
             ├── Sword/           <-- 最小单元独立小文件夹
             │   ├── Sword.tscn
             │   └── Sword.gd
             └── Gun/             <-- 最小单元独立小文件夹
                 ├── Gun.tscn
                 └── Gun.gd
     ```
   - **自洽隔离原则**：每个子实体文件夹自成一体，严禁把多个小实体的脚本与场景混杂在同一个父级文件夹下。

3. **美术素材接入（先辨别是否已有可用资源）**：
   - 先核对目标视觉素材、原始分辨率和场景用途；已有可用切片且用户要求实际视觉改造时，直接引用真实素材，不得以占位色块或空节点冒充完成。
   - 只有素材尚未交付、用户要求原型，或需暂时验证节点结构时，才使用 `ColorRect`、`PlaceholderTexture2D` 等占位，并明确交付限制。
   - 不改动原始美术资源；在场景节点上保留纹理、位置、缩放等可编辑属性，避免把整张大图写死到脚本逻辑中。

### 桌面/应用图标接入（Desktop & Application Icon Integration）

当用户要求把现有图片设为游戏桌面图标时，按以下顺序执行：

1. 先定位并检查真实素材：确认文件路径、分辨率、颜色通道和格式；保持原始图片不改写，直接以 `res://` 路径引用。不要把“图片已放入资源目录”当作图标配置完成。
2. 读取 `project.godot` 与现有 `export_presets.cfg`，确认项目级 `config/icon` 和实际桌面导出预设的图标字段。按现有预设结构做最小修改；Windows/macOS 的 `application/icon`、Linux/通用项目图标及 Android launcher 图标字段要分别核对，只有目标字段支持该格式时才复用 PNG。
3. 项目已有未提交改动时，先记录 `git status --short`，并把目标配置与原图复制到仓库外快照；修改白名单只包含用户授权的配置文件，禁止顺手格式化、移动素材或生成无关派生资源。
4. 修改后静态检查所有图标引用均指向目标资源，执行 `git diff --check`，并审计 `git diff --name-only`，确保白名单外没有本轮引入的变更。配置验证应实际运行项目指定版本的 `godot --headless --editor --path <project> --quit`；若使用 Windows 可执行文件，从当前 shell 的实际路径调用它，不要把失败的路径格式当成项目失败。
5. 交付时区分“配置解析/导出设置已验证”和“已完成真实桌面导出”；没有实际导出包或系统图标显示证据时，不宣称桌面最终显示效果。报告原图保持不变，并明确列出项目级和各导出预设字段。

**Pitfall — 只修改 `project.godot` 不能保证导出应用使用新图标**：导出预设可能覆盖项目级图标，必须检查并同步实际桌面预设的字段。

**Pitfall — 只改 Windows 字段会漏掉其他已存在的桌面目标**：遍历当前导出预设，按平台字段逐一判断；不要新增无关预设或凭空生成 `.ico/.icns`，除非用户要求或目标导出链明确需要。

**Pitfall — Headless 项目加载成功不等于图标已被系统显示**：无界面检查只能证明资源路径和配置可解析，真实系统图标仍需导出并检查生成物才能确认。

### 桌面与 Android 导出门禁

配置或验证导出时，必须使用与实际编辑器精确匹配的官方导出模板，沿用并审计现有预设，并对用户要求的每个平台执行真实导出。项目 headless 加载成功不等于导出成功；Windows 产物须做启动烟雾测试，Android APK 须做 ZIP 完整性和 `apksigner` 校验。最终汇报前重新检查产物大小/哈希及工作树副作用，且不得暴露导出日志中的签名参数或凭据。完整命令、模板安装、大小写资源修复与验证顺序见 [references/export-desktop-android.md](references/export-desktop-android.md)。

## 四、存档与交互生命周期规范 (Save & State Reset Lifecycle)：
   - 实体必须包含 `ExportSaveData() -> Dictionary` 和 `LoadSaveData(data: Dictionary) -> void`。
   - `_init()` 必须安全（支持默认参数无参构造），保证读档反序列化不崩溃。
   - **自锁与触发状态必须具备重置入口**：具有单向锁定机制（如 `stay_pressed = true`、门单向锁定）的交互组件，必须提供显式的 `ResetState()` 或新游戏/重新入场状态刷新接口，防止新场景加载或未触发保存时残留已触发状态。
   - **玩家重生 (Player Respawn) 联动重置**：关卡中依赖单次触发（如 Area2D 一次性判定、机关锁死）的交互与移动载具，须监听 `SignalBus.PlayerRespawned`。当玩家在检查点/帐篷重生且未进入不可逆阶段时，必须显式重置载具航线位置与 Area 触发锁，确保玩家重生后能够完整重新走通流程。
   - **`_ready` 初始化时序**：记录基准静止坐标（`_rest_position = position`）必须在状态位生效之前完成，且不得在场景初次加载阶段因碰撞体预重叠无条件触发持久化激活。

## 二、 AI Agent 标准 5 步实现流程

当向 AI 派发功能开发任务时，AI 必须严格按以下顺序推进：

```
[1. 查重与检索] ──> [2. 场景骨架搭建] ──> [3. 逻辑与接口编写] ──> [4. 存档与信号对齐] ──> [5. F6 独立单例测试]
```

### 步骤 1：检索、需求边界与架构对齐 (Inspect, Scope & Reuse)
* 检索 `res://Code/Autoloads/`（`Global.gd`、`SignalBus.gd`、`Util.gd`、`Data.gd`）。
* 检索 `res://Code/Common/` 查看是否有现成状态机、UI 模版或基础组件。
* 明确新建功能位于 `res://Code/Entities/BigEntity/.../SubEntity/`（严格创建专属独立小文件夹）。
* 当用户要求“先讨论章程”或仍在纠正节点职责时，先输出并确认：逻辑职责、视觉职责、变换继承、编辑器操作方式、旧实例兼容和明确不做项；确认前不得启动编码 Agent、创建实现脚本或修改项目文件。
* 把用户的最小需求原样收窄成验收标准。若只需隔离某个视觉节点的父缩放，就不要顺带引入自动生成、动态匹配、碰撞重建或全局重构。
* 修改继承场景前，同时检查基础场景、专用派生场景和真实宿主实例中的覆写；保留用户已调好的位置、缩放、碰撞层和物理尺寸。
* **先确认运行时真源再修场景**：从启动场景和 `PackedScene` 引用链追到游戏实际实例化的 `.tscn`，不要因另一个同名/拆分场景中存在正确节点就假定运行时也使用它。对比基础场景、派生场景、内联宿主副本的 `ext_resource`、子节点覆写、`tile_map_data`、纹理和 `visible`；如果宿主场景复制了旧节点而不是实例化最新拆分场景，应优先消除双真源或让宿主明确引用唯一真源，再验证初始状态。
* **首帧视觉按“数据—状态—祖先”三层排查**：① Before 节点是否真的含 TileMap 单元格/纹理；② `_ready()` 是否根据初始状态重设 `visible`，以及内容检测是否会因资源为空判定为无内容；③ 节点自身、父相位与祖先 CanvasItem 是否可见且 process/collision 切换没有误伤。这样可区分“资源根本未进入运行场景”和“初始化后被隐藏”，避免只改默认 `visible` 掩盖根因。
* 对大型且已有未提交改动的 `.tscn`，先定点查看 `git diff` 和相位/显隐脚本，再决定最小编辑区域；保留旧组件及其他相位实例，以新增专用场景接入替代直接改共享组件。
* **编码 Agent 失败时立即降级，不循环折腾调度器**：Agent 超时或 CLI 参数不兼容后，先停止仍在运行的进程，再检查目标文件的 `git status --short`、暂存区与工作区 `git diff`；已有部分修改就从现状审查补全，不能重新生成覆盖。若剩余工作已收敛为少量、低耦合的 `.gd/.tscn` 编辑，主控直接完成并验证；只有仍属跨模块重构时才更换 Agent 路线。
* 拼景改造先划清三类坐标与运动：远/中/近背景的镜头视差（可用多个 `Parallax2D`，不等于自动平铺）、局部云水植物的自身动画、砖块前景的世界坐标或移动砖块子节点继承运动。不要给贴砖装饰施加视差，否则镜头移动时会和砖块错位。
* **运行时背景可见性优先于边界治理**：用户要求“进入场景就能看到背景”时，第一轮实现只建立真实素材、分层与视差，不主动添加 `clip_contents`、`limit_begin`/`limit_end`、`scroll_offset`、区域显隐脚本或循环。先从项目启动场景沿实例链追到实际宿主，检查基础场景、宿主关卡和最终入口场景对背景实例的 `position`、`scale`、`top_level`、`visible` 覆写；宿主覆写会优先于子场景内的摆放，常把编辑器里正确的背景在 F5 时再次移出镜头。只有真实运行画面已可见，且用户明确要求限制越界后，才逐项增加边界机制，每增加一项都重新做 F5 宿主画面验证。
* **整幅拼接背景先冻结构图，再替换运动模型**：当多张图片已经拼成用户认可的最终画面时，先记录并保持每个子图的纹理、局部坐标、缩放、翻转、`z_index` 和父子顺序；若用户要求景深，再按视觉语义拆为远/中/近层，保持构图不变，仅让各层承担不同的 `scroll_scale.x`，并将 `scroll_scale.y = 0` 锁死。不得为了“方便管理”顺带重排素材、添加碰撞或改变玩法节点。
* **有限区域背景先证明可见，再讨论限制**：默认令 `repeat_size = Vector2.ZERO`，不把非无缝素材强行循环。`Parallax2D.limit_*` 限制的是滚动范围，Control 裁剪限制的是绘制区域，`scroll_offset` 改变的是实际显示位置，三者不能混用；在宿主带平移/缩放时，按错误坐标空间计算会把整层推到视口之外。除非已取得真实关卡矩形、完成坐标系换算，并在实际入口的左/中/右边界做过画面验证，否则不要添加这些限制。
* **分层视差（Parallax2D）梯度与配置全覆盖**：
  - **排查总控与默认开关**：当背景出现“移速与前景/摄像机完全一致”时，首先检查配置单例（如 `ExportSettings`）或场景导出的视差总控开关（`parallax_enabled`）；若默认被关闭，图层速度会全部退化为 1.0 同步移动。
  - **图层速率映射完整性**：遍历各视觉层（Sky、FarBackground、MiddleBackground、Foreground 等）赋予 `scroll_scale` 时，确保每层都在配置项和脚本条件分支中有明确映射，严禁遗漏天空（Sky）等最底层背景。
  - **阶梯速率拉开景深**：视差梯度必须显著拉开才能产生透视感（如 Sky 0.2、Far 0.5、Middle 0.8、Foreground 1.05~1.1）；中远景如果设为 0.85/0.96 则层次感极其微弱，在玩家移动时与前景几无差异。
  - **大世界多关卡视差背景越界治理按最小机制选择**：先判断背景是有限区域构图还是连续底层。有限构图优先用非重复、固定边界和宿主生命周期限制；不要一上来写相机显隐脚本。仅当局部背景采用 `Parallax2D` 后仍会在相邻关卡可见，且宿主无法自然卸载或裁剪时，才按相机世界坐标判定区域并切换 `visible`；边界参数应暴露在合适的配置位置，避免硬编码散落。
  - **关卡布景复用与运行期不可见排查（Bounds 空间与宿主覆写双重校验）**：
    - **严防跨关卡边界错位**：复用既有关卡的视差裁剪脚本时，必须将 `ExportSettings` 中的 bounds 替换为当前关卡独立的专属范围，且计算 `camera_x` 时必须转换为当前父关卡节点的本地坐标（`phase.to_local(camera_world).x`）。若直接复用其它关卡（如将去程/绿洲的 bounds 照搬至沉没宫殿），因绝对世界坐标差异，`in_level` 会在首帧永久判假，导致所有子层每帧被动态置为 `visible = false`。
    - **静态宿主覆写与动态脚本双层排查**：当场景运行期背景完全不可见时，优先排查两层：① 宿主关卡 `.tscn` 中该实例节点本身是否带有 `visible = false` 覆盖；② 挂载脚本的 `_process` 中是否有视口裁剪逻辑因阈值不匹配每帧将图层隐藏。
* **先分离连续底层与区域构图，再设置循环**：只有需要跨区域保持连续、且纹理本身可无缝衔接的天空/远山进入重复 `Parallax2D`；月亮、云、地面、绿洲、遗迹和前景装饰放入普通世界空间容器，由关卡按区域手摆。`scroll_scale` 只决定随摄像机滚动的比例，`repeat_size` 才决定循环；`repeat_size = Vector2.ZERO` 表示不循环。循环周期必须来自实际纹理像素尺寸并结合 Sprite 缩放核对，不能用关卡总宽或目测值。
* **先锁定拼接轴，再布置副本与循环周期**：用户说“横向/竖向衔接”时，将其作为明确的不变量，不得按常见横向卷轴习惯自行改轴。横向循环只设置 `repeat_size.x`，竖向循环只设置 `repeat_size.y`，另一轴保持 `0`；若使用一张原图加一张轴向翻转图构成镜像循环单元，按贴图在场景中的实际显示尺寸 `w/h` 放置副本，并使用对应的 `flip_h/flip_v`，周期为该轴两张图的总跨度（如竖向原图与相邻镜像图为 `Vector2(0, 2h)`）。修改前检查现有副本与 `repeat_size` 是否成套：副本已删但周期仍在会让引擎继续重复一个不完整单元并露空；不需要循环的图层应同步清为 `Vector2.ZERO`，保留各层独立 `scroll_scale` 以维持景深。
* **轴向拼接分结构验证与画面验收**：用项目外临时 `SceneTree` 脚本真实 `load()`、`instantiate()` 场景，并断言循环轴、周期、副本位置、翻转方向、非循环层 `repeat_size` 与前后景不同 `scroll_scale`；这只证明配置和加载正确。仍须在真实宿主中沿循环轴移动镜头检查接缝、露空与跳变，未做画面检查时不得宣称“视觉无缝”。
* **局部 `Parallax2D` 先验证宿主变换，再决定是否隔离**：普通世界空间背景若应随阶段根节点整体平移、缩放、显隐或卸载，应保留父级变换，不要为对齐方便随手设 `top_level`。但 `Parallax2D` 会基于画布/摄像机再次计算偏移；当真实宿主实例自身带有平移或非单位缩放时，继承变换可能与视差计算叠加，把图层推离视口。遇到“节点已实例化且 `visible=true`，画面却完全不出现”时，在完整宿主中记录背景根节点的 `global_position`/`global_scale`、摄像机世界中心及各层屏幕矩形，再做内存 A/B：临时设 `top_level = true` 与 `global_transform = Transform2D.IDENTITY`。只有 A/B 证明父变换是根因，且区域生命周期仍由父节点引用或独立边界逻辑控制时，才将隔离变换落盘；不得用逐层硬编码偏移抵消宿主变换，因为关卡位置或缩放调整后会再次失效。若背景确需继承关卡移动，则改正坐标系或场景层级，而不是隔离变换。
* **重组 `.tscn` 节点层级时同步所有路径消费者**：移动或删除节点后，逐项更新 `AnimationPlayer` 轨道 `NodePath`、宿主场景中的实例覆写路径、`editable path`、脚本导出 `NodePath`、节点索引和仅由旧覆写使用的 `ext_resource`。先搜索旧节点名确认没有残留，再做资源 ID 完整性和 `git diff --check` 静态门禁；否则基础场景文本正确，真实宿主仍会因陈旧覆写加载失败或继续生成旧内容。
* **限制 `Parallax2D` 覆盖范围前先确认边界语义**：从真实宿主场景、摄像机限制/门、关卡碰撞或明确的场景分段节点中取得当前段的世界矩形，并换算到该 `Parallax2D` 的坐标系；不得用贴图总宽、最远子节点位置或目测值代替场景边界。分别核对 `limit_begin`/`limit_end`、`scroll_scale`、`scroll_offset`、`top_level` 与父级平移，因为 limit 约束的是视差滚动范围，不等同于裁剪超出矩形的子 Sprite。若需求是“只绘制当前场景”，除设置正确 limit 外，还要按实际边界缩短/隐藏越界铺图，或使用独立裁剪区域；不得仅加 limit 后宣称已限制绘制范围。
* **背景边界改动必须做边界点验证**：至少在当前段左端、中部、右端和相邻场景交界处运行真实宿主场景，检查无露底、无跨段残留、无进入时跳变；同时确认非重复层 `repeat_size = Vector2.ZERO`。只有静态 diff/解析时，只报告属性已修改和静态检查通过，不宣称画面覆盖范围已经修好。

### 步骤 2：场景骨架与占位符装配 (Scene Assembly w/ Placeholders)
* 在对应子实体专属小文件夹内创建 `.tscn` 场景文件。
* 预先在场景树中摆放好所有子节点（如 `CollisionShape2D`, `AnimationPlayer`, `Timer`, UI 容器等）。
* **配置占位贴图**：使用 `PlaceholderTexture2D` 或 `ColorRect` 明确尺寸规格（如 32x32）。
* 针对 UI，配置好 `Control` 节点的锚点系统。

### 步骤 3：脚本逻辑编写与规范落地 (Script Implementation)
* 在该独立小文件夹下创建同名主脚本（如 `SubEntity.gd`）。
* 使用 `@onready` 获取预置节点引用。
* 公开方法写大驼峰 + `##` 详细注释（入参、返回值、调用约束）。
* 私有方法写 `_snake_case`。

### 步骤 4：信号总线与存档接口集成 (Integration)
* 如果涉及全局事件广播，检查 `SignalBus.gd` 是否有对应大驼峰信号，如无则在 `SignalBus.gd` 增量追加并补充 `##` 注释。
* 实现 `ExportSaveData()` 与 `LoadSaveData()`。

### 步骤 5：单元验证与交付 (Verification Gate)
* 验证该场景可以独立按 **F6**（运行当前场景）进行测试，不依赖未初始化的主场景环境。
* **背景不可见时按实际入口做确定性排查**：不要继续盲摆节点。依次检查：① F5 实际入口是否引用目标关卡；② 最终入口/宿主 `.tscn` 是否对实例覆写了 `position`、`scale`、`top_level` 或 `visible`；③ 脚本是否在 `_ready/_process` 改写显隐或视差偏移；④ 祖先 `CanvasItem` 是否隐藏；⑤ `clip_contents`、`limit_*`、`scroll_offset` 与宿主变换是否把各层推离视口；⑥ 摄像机世界矩形与每层全局可视矩形是否相交。先删除未经证明必要的裁剪/限制/偏移，恢复“必定可见”的最小版本，再逐项恢复效果。独立子场景 `visible=true` 或成功实例化不能证明 F5 可见。
* **命令行/Headless 闭环测试交付门禁**：
  - 严禁未经运行期测试直接宣称修复完成交付用户。
  - 向 AI/Codex 下达任务时必须明确提供 Godot 引擎 CLI/Console 路径（如 `godot_console.exe --headless --script <test_script.gd>`）。
  - 要求编写独立的临时测试脚本或针对性测试用例，真实执行 Headless 实例化、状态转换验证与存读档还原测试，并在通过后清理临时脚本。
  - 独立场景验证之后还要加载实际入口/聚合宿主场景；对 `Parallax2D` 等依赖摄像机、父级变换或区域裁剪的节点，至少输出背景实例的最终全局变换、可见性、裁剪状态和层级参数，并验证其可视矩形与目标摄像机视口相交。项目全入口若受无关既有错误干扰，可用只加载目标宿主链的最小测试隔离验证，但必须明确这不等于完整 F5 画面验收。
* 确保控制台无本次改动引入的报错或 Missing Dependency；不要把仓库已有无关错误包装成当前功能失败或成功。
* 视觉拼景还须实测编辑器中的实际可见画面：遍历镜头可达范围检查拼接缺口、遮挡与相位显隐；对照源图尺寸与 Sprite2D 缩放/过滤检查放大模糊，局部动画只驱动必要对象，避免逐帧重建整层。Headless 实例化只证明场景能加载，不证明清晰、美观或完整覆盖。
* 交付同时写清编辑器里每层的节点路径、可调的纹理/位置/缩放/视差及砖块前装饰如何放置；只宣称已由运行输出和画面检查证实的效果。

### 从宿主内联节点迁移为组件派生场景

当大型关卡把同一组件的多套视觉节点直接内联在宿主 `.tscn` 中，而这些布局应由组件目录维护时：

1. **先把现状当作取证源，不当作最终结构**：从 Git 基线与当前工作树分别提取每个实例的节点块，记录节点数量、名称、位置、旋转、缩放、翻转、纹理及其他非默认属性；不得用一套“近似默认布局”替代多个已调好的变体。
2. **建立“空基础组件 + 专用派生场景”结构**：基础场景只保留通用逻辑、空视觉容器和必要的跟随/显隐节点；每套布局各自进入组件目录下的派生 `.tscn`，宿主只实例化对应变体并保留实例级参数覆写。不要让基础组件默认携带一枚示例视觉，否则所有通用实例都会意外显示。
3. **定点替换宿主，不重写大型场景**：只替换相关 `ext_resource`、实例头和旧内联节点块；保留碰撞、TileMap、Shader、材质、脚本导出值和无关未提交改动。迁移后搜索旧内联父路径，确认宿主不再持有视觉副本，避免双真源。
4. **对迁移数据做结构化等价比较**：用确定性脚本分别解析历史节点块和派生场景节点块，忽略只因资源归属变化而不同的纹理引用行，其余属性逐节点比较，并断言每套数量及总数。仅凭 `git diff` 目测不足以证明几十个节点没有漏项或串位。
5. **运行期验证基础与变体**：用项目外临时 `SceneTree` 脚本真实 `load()`/`instantiate()` 基础场景、全部派生场景和最终宿主；断言基础容器为空、各变体数量正确、初始显隐正确，并实际调用状态切换验证视觉与碰撞同步。测试输出必须包含可识别的成功标志。
6. **隔离并清理测试副作用**：运行 Godot 前保存 `git status --short` 与目标文件定点 diff；运行后再次比较。若编辑器扫描或游戏启动改写存档、宿主序列化或无关场景，只逆转本次测试新增且已确认测试前干净的差异，绝不能把用户原有脏文件直接恢复到 `HEAD`。

**Pitfall — 派生场景迁移后仍在宿主保留内联节点会形成双真源**：后续编辑只会更新其中一份，运行时可能继续加载陈旧布局；宿主必须只引用唯一的组件变体。

**Pitfall — Godot Headless 验证也可能产生项目写入**：自动存档、资源导入或场景重序列化会污染工作树；必须以前后状态差异识别副作用，而不是把测试后的所有变化一并提交或清理。

### 常驻阶段场景同步（Persistent Phase Scenes）

当聚合关卡把内嵌阶段拆成独立 `PackedScene`，并要求多个阶段同时常驻时：

1. 先把每个阶段当前节点子树完整迁入对应 `.tscn`，核对根节点名、UID、`ext_resource`/`sub_resource`、实例覆写、导出 `NodePath`、信号和 editable path；聚合场景只保留阶段实例，避免“内嵌副本 + 独立场景”双真源。
2. 聚合脚本只引用常驻实例并切换激活状态，不再 `instantiate()`、`queue_free()`、`add_child()` 或 `remove_child()`。在 `.tscn` 中预先把非初始阶段设为 `visible = false` 和 `PROCESS_MODE_DISABLED`，防止父节点 `_ready()` 前出现首帧处理。
3. 停用阶段时递归关闭可见性、处理和碰撞；恢复时必须还原每个 `CollisionObject2D` 原有的 `collision_layer`/`collision_mask`，以及每个 `TileMapLayer` 原有的 `collision_enabled`。禁止统一恢复成 `1/1`，因为触发区、终点和伤害区常使用不同遮罩。
4. 记住 `PROCESS_MODE_DISABLED` 不阻止 `_ready()`：常驻阶段中的 `_ready()` 不得产生不可逆副作用；需要延迟的行为拆到显式激活入口，并保证重复启停幂等。
5. 静态门禁至少检查：资源 ID 均有定义、`res://` 路径存在、脚本中的节点路径在组合场景中可达、切换代码不含动态增删阶段节点、`git diff --check` 通过。随后用 Godot Headless 实例化聚合场景并实际切换两次，确认输入、计时器、动画、碰撞和信号不会双重运行；没有引擎运行结果时明确只报告静态检查。

**Pitfall — 隐藏 CanvasItem 不会关闭物理碰撞**：阶段常驻后若只切 `visible`，不可见阶段仍会挡路或触发 Area；碰撞必须独立递归停用并按原值恢复。

**Pitfall — 禁用父节点处理不等于取消初始化副作用**：子节点仍会进入树并执行 `_ready()`，所以一次性启动、信号发射和状态写入不能只靠 `process_mode` 防护。

### 可替换纹理的伸缩机关（固定显示空间）

当升降突刺、地刺或类似机关已有运动与碰撞逻辑，而用户只需稍后自行替换美术时：

1. 先检查基础场景、关卡派生场景和负责绘制的脚本，确认真实的可视节点与局部坐标系；不要改动运动、伤害或碰撞逻辑。
2. 在关卡专用视觉节点上暴露一个可空的 `@export var ..._texture: Texture2D`，让用户能直接在 Inspector 拖入完整透明 PNG；留空时保留旧纹理作为回退，避免现有关卡变空。
3. 明确定义固定显示矩形，以机关地面线为裁切基准。动画只改变已显示高度或视觉根节点的位置：完全埋下时不可见，伸出时从基准线连续露出，完全伸出时显示完整纹理。
4. **必须保证编辑器内所见即所得（WYSIWYG）**：使用 `@tool` 脚本绘制伸缩机关时，严格区分 `Engine.is_editor_hint()` 与运行期逻辑。运行期默认状态可为“完全缩回/高度 0/埋入隐藏”，但在编辑器环境下，默认必须按**完全伸出状态**（完整尺寸与最高位置）进行绘制呈现，严禁在编辑器里直接隐藏或将绘制高度置 0。关卡设计与策划需要直观查看机关形态、地面贴合线与间距，在 2D 视口中必须可直接摆放查验。
5. 自定义完整纹理默认读取整张源区域；只有旧资源确实来自图集时，才保留旧的源矩形裁切。不要把新纹理继续绑死在旧图集坐标上。
6. 若机关横向重复铺设，按机关宽度计算重复数量与步长，但源纹理宽高比、裁切方向和底线必须保持一致；不得通过缩放碰撞体适配画面。
7. 交付时只告诉用户 Inspector 中准确的节点路径、导出字段和素材约束；若没有 Godot 运行验证，只报告静态解析或 diff 检查结果，不宣称动画已实机通过。

**Pitfall — 不要为“之后只换纹理”要求逐帧动画**：已有连续升降状态时，固定显示空间加位置/高度裁切更易复用，也能让单张透明 PNG 完成埋入与露出效果。

**Pitfall — 伸缩/隐藏类机关在 `@tool` 下切忌把运行时初始隐藏带入编辑器**：若在编辑器里沿用运行时 `visible = false` 或 `visible_height = 0`，关卡设计拖入场景后将完全不可见，无法对齐地面或摆放。编辑器视图必须固定显示完整展开形态。

**Pitfall — 导出字段必须放在用户实际选中的关卡专用节点上**：放到基础脚本但 Inspector 中无法从目标实例直接配置，会增加使用成本并容易改错共享资源。

### 美术动画接入关卡节点（Asset-to-Scene Integration）

当任务是把已预处理动画挂到现有关卡实体时，按以下顺序执行：

1. **先定位语义节点，并判断视觉坐标系**：搜索目标关卡 `.tscn`、其脚本和实例化子场景，确认真正承担 Boss 移动、碰撞和伤害逻辑的节点。普通世界空间动画可作为该逻辑节点的视觉子节点以继承运动；若需求明确绑定摄像机边缘、视口尺寸或屏幕侵染，则拆成独立视觉实体，但追逐轴必须直接投影逻辑节点的当前世界位置/碰撞前沿，不得读取速度后再次积分或模拟运动。
2. **先保护现场**：运行 `git status --short` 和目标文件的定点 `git diff`；只编辑本任务目标，不清理用户已有修改。
3. **资源与场景分离**：将逐帧 PNG 组装为独立 `SpriteFrames` `.tres`，显式设置帧顺序、FPS、循环和动画名；在 `.tscn` 中仅引用资源并新增 `AnimatedSprite2D`。这样可替换动画而不碰 Boss 逻辑。
4. **对齐可视与物理基准**：使用统一画布/底线的帧，并以局部 `position` 对齐现有碰撞体；隐藏被正式美术取代的视觉占位节点，但不得删除或隐藏承载碰撞、触发、伤害的节点。
5. **分两阶段验证**：
   - 先运行 Godot `--headless --editor --path <project> --quit`，触发资源导入并检查解析。
   - 再用项目外临时 `SceneTree` 脚本 `load()` + `instantiate()` 目标场景，断言动画节点存在、资源非空、帧数/FPS/循环/autoplay/位置正确，以及占位视觉已隐藏；测试成功标志必须来自真实控制台输出。
6. **交付只报告已验证事实**：列出接入节点路径、动画参数、保留的逻辑行为和测试输出；不要附带未在本次命令输出中观察到的“既有报错”。

**Pitfall — 不要只验证 `.tres` 文本格式**：Godot 的外部资源路径、继承场景覆盖和节点索引可能在文本看似正确时仍加载失败，必须实际实例化目标场景。

**Pitfall — 不要把宽精灵表直接塞进场景后凭 `hframes` 猜切片**：已有逐帧标准化输出时优先构建显式 `SpriteFrames`，因为它固定帧序、便于逐帧替换，也能避免画布或导入边界差异造成串帧。

**摄像机边缘追逐视觉**：

1. **先把需求写成分轴不变量**：明确追逐轴、正交轴、显隐条件和不可见边界，再编码。左右追逐时，X 只由物理前沿决定，Y 每帧精确锁定玩家；上下追逐时，Y 只由物理前沿决定，X 每帧精确锁定玩家。用户要求“咬住”时不得擅自加入平滑、延迟或视觉 tween。
2. **确定唯一真源**：逻辑 mover 继续作为世界位置、方向、速度、碰撞、伤害和启停时序的唯一真源；视觉实体只读取其当前绝对状态，不复制、改写或二次模拟追逐逻辑。
3. **从真实物理边界取值**：优先读取 `CollisionShape2D` 的形状与全局变换，将矩形四角 `to_global()` 后沿追逐方向做点积，取最大值作为 leading edge；不要只用 mover 原点，因为碰撞体偏移、缩放和旋转会改变实际接触边界。
4. **计算摄像机世界矩形**：用当前 viewport 可见尺寸除以 `Camera2D.zoom` 得到世界尺寸，并以 `get_screen_center_position()` 为中心；不得假定固定分辨率。目标节点优先使用显式 `NodePath`，可再以稳定的玩家 group 作为回退，并处理重生后旧引用失效。
5. **直接映射追逐轴，锁定正交轴**：每个物理帧以 leading edge 与摄像机对应边界的有符号距离计算显隐及 Boss 前沿坐标；正交轴中心直接采用玩家当前世界坐标。向右从左侧进入、向左从右侧、向下从上侧、向上从下侧。物理体停下、瞬移、反向，或玩家/摄像机移动缩放时，都必须在同一帧按当前几何关系重算。
6. **禁止启用即露出**：追逐组件激活只允许开始读取几何状态；物理前沿尚未越过摄像机边界时，视觉必须完全隐藏。不得用固定 `initial_reveal_ratio`、初始推进量、计时器或启用 tween 强制露出；进入感只能来自物理前沿逐步穿入视野。
7. **让正交边界永不入镜**：动画和相关遮罩在正交轴上以玩家为中心，并覆盖“玩家到两侧最远可见边界的两倍 + Shader 最大扭曲 + 安全余量”。若玩家受限于镜头范围，可采用至少 `2 × camera_span + 2 × safety_margin` 的保守尺寸；不能只用 `1.1 × viewport`，否则玩家靠近镜头边缘时会看到贴图上下/左右边界。
8. **用独立纯黑几何遮罩封住后方**：在 `.tscn` 中预置 `Polygon2D` 等不透明纯黑节点；遮罩从当前物理前沿连续延伸到已吞噬侧的屏幕外缘。Boss 动画/Shader 只表现前沿的模糊、扭曲、噪声和蠕动，不承担黑幕后区或追赶判定；前沿与遮罩需有足够重叠，避免 Shader 扭曲时露缝。
9. **验证几何不变量而非“看起来同步”**：项目外临时 `SceneTree` 测试至少覆盖四方向、前沿在视野外时隐藏、越界后按侵入深度渐进显示、物理前沿移动 N 世界单位时视觉前沿和遮罩边界也移动 N、玩家只沿正交轴移动时视觉中心同量跟随、玩家位于镜头两端时视觉边界仍在镜头外，以及不同 viewport/zoom。实例化真实宿主场景并断言 `CollisionShape2D`、`KillArea`、`WarningWall`、`LeadingEdge` 仍在。
10. **最后做真实画面验收**：Headless 数值测试不能证明没有跳出、露边或遮罩缝。进入实际关卡观察完整进入过程，并分别移动玩家与摄像机到正交轴两端，检查启用瞬间、Shader 最大扭曲和变焦状态；没有画面证据时，只报告几何测试通过，不得声称视觉已经验收。

**Pitfall — 读取 mover 速度后执行 `advance += speed * delta` 仍是脱钩模拟**：即使速度数值相同，启动时机、暂停、传送、摄像机移动和帧累计也会造成偏差；视觉不得拥有独立速度、计时器、累计距离或归一化追赶进度。

**Pitfall — 不要把“跟随摄像机中心”误当成“咬住玩家”**：两者仅在玩家居中时重合；正交轴必须明确取玩家坐标，并在玩家重生后重新解析目标引用。

**Pitfall — 不要用放大一点的贴图解决边界问题**：正交轴跟随玩家会让贴图中心偏离镜头中心，普通 viewport 倍率仍会露边；按最坏位置差计算覆盖尺寸并加入 Shader 安全余量。

**Pitfall — 不要用动画透明区冒充后方遮罩**：放大纹理和 Shader 边缘会暴露透明空洞或贴图矩形边界；后方必须由独立不透明黑色几何覆盖到屏幕边缘。

**Pitfall — 不要因替换视觉而删除旧逻辑子树**：视觉节点可能与 mover 同层或被继承场景覆写，删除父级会连带破坏碰撞和伤害判定。

### 4. 追逐器正交跟随与后方幕布吞噬（Chase Mover Orthogonal Tracking & Shroud）

当实体依托单向线性推进组件（如 `DirectionalChaseMover`）同时需要对玩家进行正交轴跟随（如向右追逐时对齐玩家 Y 轴）及身后关卡吞噬时：

1. **分层职责划分，不污染底层通用组件**：
   - 保持底层推进组件（如 `DirectionalChaseMover`）的纯粹性，它仅负责主推进轴的速度、加速度和距离推进。
   - 正交轴跟随（Y 轴跟踪）与关卡级视觉幕布遮罩必须封装在具体的顶层业务实体（如 `OasisBattlefieldChaser`）中，确保底层组件在其他方向或其它关卡复用时不被破坏。
2. **正交轴平滑缓动与配置暴露**：
   - 在平台跳跃关卡中，主角跳跃、下落或使用能力时 Y 坐标会快速起伏。若追逐体直接硬赋值对齐玩家 Y 坐标，会导致追逐巨怪画面生硬颤抖或瞬移。
   - 应暴露 `@export var follow_player_y: bool = true` 和 `@export var y_follow_speed: float = 6.0` 参数，在 `_physics_process` 中使用 `lerpf(global_position.y, _target.global_position.y, y_follow_speed * delta)` 平滑插值。
   - 仅在追逐器处于活跃激活状态（`mover.IsActive()`）时才执行跟随，待机或结算时冻结，避免未入场或结算时乱飘。
3. **后方吞噬幕布 (Trailing Shroud) 的范围与生命周期控制**：
   - 若需求为“走过之处视觉上彻底被纯色/黑色幕布遮盖”，在追逐者根节点下挂载 `ColorRect` 或 `Polygon2D`（设置 `top_level = true` 或在全局空间重算尺寸）。
   - **动态边界扩展**：幕布的后沿（左边界）必须锁定在追逐起点后方足够的安全边界（`minf(origin_x - margin, current_x - margin)`），前沿紧随当前追逐体前沿（`current_x + offset`），垂直方向覆盖关卡视口极限跨度（如上下各 5000 像素），确保玩家即使拉远镜头也绝不露缝。
   - **状态联动生命周期**：幕布在初始状态必须显式隐藏；在实体调用 `StartChase()` 激活推进时显式点亮，在 `ResetChase()` 或 `EndChase()` 时自动随实体隐藏或重置尺寸，防止重开或阶段结算时常驻幕布遮挡后续内容。

**Pitfall — 严禁把正交跟踪直接写进通用主向推进组件**：通用组件若写死 `player.global_position.y`，会导致该组件未来用于纯横向、纯纵向、固定轨道或非玩家目标的追逐时产生隐蔽耦合与报错。

**Pitfall — 动态延伸幕布切忌使用固定屏幕尺寸**：若使用固定屏幕宽高的 ColorRect 随追逐体移动，当玩家回头或摄像机大幅变焦时，追逐体后方已经“走过”的关卡区域会再次漏出；幕布必须是从**出发原点**持续拉伸至**当前最前沿**的连续区域。
